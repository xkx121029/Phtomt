## 一、优化目标

提示词优化的本质目标只有三个，按优先级排列：

| 优先级 | 目标 | 衡量指标 |
|--------|------|----------|
| P0 | **决策准确率**——让模型输出的动作正确、可执行 | 决策逻辑通过率、端到端任务成功率 |
| P1 | **输出稳定性**——同样的输入尽量得到一致的正确输出 | 格式正确率、字段齐全率、回归基准一致率 |
| P2 | **成本效率**——用最少的 token 达到前两个目标 | 单任务 token 消耗、云端调用次数 |

**一句话原则：准确率是命，稳定性是底线，成本是锦上添花。三者冲突时，前两个永远优先。**

## 二、优化原则

### 2.1 先问"这个约束能不能让模型犯错"，再问"这个约束省不省 token"

Prompt 中每加一条规则，都要问两个问题：
1. 这条规则能防止什么错误？
2. 这条规则会不会引入新的误解？

**反例**：在 Prompt 中写"请仔细分析每一个控件"，这句话既不能防止错误，又增加了模型的"思考负担"，属于无效内容。

**正例**：写"source=accessibility 时禁止使用 coordinate 寻址"，这条规则能防止一个具体的高频错误（有 id 却用坐标），价值明确。

### 2.2 规则优于示例，示例优于空话

```
规则（最有效）：必须用 method="id"，禁止用 coordinate
    ↓ 规则表达不清时才用示例
示例（次有效）：{"action":"tap","target":{"method":"id","value":"node_1"}}
    ↓ 只有示例才需要配说明
空话（无效）：请认真选择正确的寻址方式
```

### 2.3 一条规则只约束一件事

把复合规则拆开。不要写"如果页面有弹窗且弹窗有关闭按钮且用户任务不是处理弹窗，则点击关闭按钮"——这太复杂，模型容易漏掉条件。

拆成两条：
- "页面上有弹窗时，先处理弹窗，再执行原计划"
- "弹窗处理顺序：正向按钮 > 关闭按钮"

### 2.4 反面示例和正面示例同等重要

模型看反面示例，学到的不是"什么是对的"，而是"什么是绝对不行的"。对于格式类约束（不输出 markdown、不加解释文字），反面示例比正面示例更有效。

### 2.5 约束写在"触发点"附近

约束规则要写在它生效的地方，而不是堆在开头。比如"倒计时广告的处理规则"，应该放在页面数据说明之后、动作类型之前，而不是和"铁律"混在一起。

## 三、优化手段清单

### 3.1 结构优化

| 手段 | 说明 | 预期收益 |
|------|------|----------|
| 分层标题 | 用 `#` 标题把规则分块（铁律 / 数据格式 / 寻址 / 动作 / 决策原则） | 模型更容易定位规则 |
| 铁律前置 | 把"输出纯 JSON"等最高优先级规则放在最前面 | 降低格式错误率 |
| 表格替代段落 | 字段约束、动作类型用表格而非大段文字 | 减少 token，提升理解 |
| 末尾重申 | 每条 Prompt 末尾重复"只输出 JSON" | 对抗"长上下文遗忘" |

### 3.2 内容优化

| 手段 | 说明 | 预期收益 |
|------|------|----------|
| 去空话 | 删除"请仔细""务必""认真"等无信息量的词 | 省 token，减少噪音 |
| 给枚举不给描述 | 写 `direction: up/down/left/right`，不写"可以向上、向下、向左、向右滑动" | 降低越界风险 |
| 给格式给示例 | 每个动作类型配一个完整 JSON 示例 | 提升字段齐全率 |
| 显式列禁止项 | 用"禁止/绝不/不允许"明确负面约束 | 降低特定错误 |

### 3.3 逻辑优化

| 手段 | 说明 | 预期收益 |
|------|------|----------|
| 优先级排序 | 写"优先 A，其次 B"而非"A 或 B" | 让模型在模糊场景下有确定选择 |
| 条件分支表格化 | 用"如果…则…"表格替代嵌套文字 | 减少漏判 |
| 状态传递规范化 | 用固定格式"✅ 已确认成功 / ⚠️ 已发送但未确认 / ❌ 未生效"传递上一步结果 | 消除模型的错误假设 |
| 失败路径预定义 | 明确"如果找不到目标控件 → 输出 abort"等兜底行为 | 减少死循环 |

### 3.4 动态优化（端侧配合）

| 手段 | 说明 | 预期收益 |
|------|------|----------|
| Prompt 分级 | 根据页面复杂度选 MINIMAL / STANDARD / FULL 三级 | 简单场景省 token |
| Few-shot 按需注入 | 只有冷门场景才注入示例 | 常规场景少噪音 |
| 用户偏好注入 | 规划时注入相关偏好子集 | 提升个性化准确率 |
| 增量页面协议 | 页面变化小时只传 diff | 大幅省 token |

## 四、优化流程

每次 Prompt 变更必须走完整流程，禁止"改了直接上线"。

```
第 1 步：明确问题
    ↓  记录现象（例如：模型在搜索结果页有时输出 coordinate 寻址）
第 2 步：定位原因
    ↓  分析是规则缺失、规则不清、还是规则冲突
第 3 步：设计修改
    ↓  按"一条规则约束一件事"原则改，记录改动点
第 4 步：回归测试
    ↓  跑第二层 Prompt 回归测试（组 A~E 全量）
第 5 步：对比指标
    ↓  对比修改前后：格式正确率、决策通过率、token 消耗
第 6 步：决定是否保留
    ↓  指标提升 → 保留；指标持平或下降 → 回滚
第 7 步：记录到变更日志
        ↓  记录"改了什么、为什么改、效果如何"
```

## 七、已知的优化边界

不是所有问题都能靠改 Prompt 解决。以下情况应当停止在 Prompt 上使劲，转而去改代码：

| 现象 | 根因在代码还是 Prompt？ | 正确做法 |
|------|----------------------|----------|
| 模型输出了合法 JSON，但动作执行后页面没反应 | 代码（执行层/验证层） | 改 VerifiedClickExecutor 和 RobustStepVerifier |
| 模型"没做却以为做了" | 代码（历史记录的 isConfirmed 逻辑） | 改 StepRecord 的状态传递 |
| 弹窗、加载类场景大量调用云端 | 代码（端侧决策引擎没生效） | 改 LocalDecisionEngine |
| 页面数据本身不完整（控件缺失、文字丢失） | 代码（感知层解析器） | 改 AccessibilityTreeParser |
| 模型反复输出格式错误（非偶发） | 两边都有 | 先查 JSON Mode 是否开启，再查 Prompt 铁律是否前置 |

**判断标准：如果 20 次调用里超过 1 次格式错误、或超过 2 次决策逻辑错误，先怀疑代码层面的数据质量，而不是继续加 Prompt 规则。**

## 八、优化优先级路线图

按投入产出比排序，建议的优化顺序：

| 优先级 | 优化项 | 预期收益 | 成本 |
|--------|--------|----------|------|
| P0 | 铁律前置 + 末尾重申（确保纯 JSON 输出） | 格式正确率逼近 100% | 低 |
| P0 | 枚举值表格化（action/keycode/direction 全部给枚举） | 越界错误大幅下降 | 低 |
| P1 | 寻址策略用条件分支表格 | 寻址错误下降 | 低 |
| P1 | 执行状态三态规范化 | 消除"以为做了"的认知偏差 | 低 |
| P1 | 每个动作类型配完整示例 | 字段齐全率提升 | 中 |
| P2 | 倒计时广告规则前置为高优先级 | 误触率下降 | 低 |
| P2 | 动作合并规则明确化 | 云端调用次数下降 | 低 |
| P3 | 动态 Prompt 分级 | token 消耗下降 | 中（需端侧配合） |
| P3 | Few-shot 按需注入 | 冷门场景准确率提升 | 中 |
