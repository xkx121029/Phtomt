# 任务文档 v2：格式与接口（手机端接入约定）

> 服务：hpa-trainer（容器内 `8080`，NAS 映射 `9817`）
> 代码：`D:\mobilegym_test\hpa_training\taskdoc.py`（生成 + 检索 + 同步）、`api.py`（HTTP 面）
> 状态：`schema_version = 2`，当前线上 39 份文档，整包 219 KB

---

## 0. 与 v1 的区别

v1 是「第 1 步点这里、第 2 步输入 xxx」的轨迹回放，只能照着抄。
v2 改成「怎么达成目标」：成功条件、前提、判断点、陷阱、收尾校验在前，动作序列降级为
`reference_steps`（参考实现之一），不参与决策。

---

## 1. 文档结构（单份 JSON）

`GET /api/taskdoc/{task_id}` 返回的完整对象。字段分四组：

### 1.1 身份与检索元数据

| 字段 | 类型 | 说明 |
|---|---|---|
| `schema_version` | int | 固定 `2` |
| `task_id` | str | 主键，如 `alipay.AnalyzeSpending` |
| `task_name` | str | 本次轨迹里的任务描述（含随机参数时以它为准） |
| `catalog_task_name` | str | 任务目录里的原始描述 |
| `trajectory_task_name` | str | 轨迹记录的任务描述 |
| `param_mismatch` | bool | 两者不一致（随机参数/改写）时为 true |
| `app` | str | 归一化 App 名：`alipay` / `bilibili` / `notes` / `account` / `wechat_reading` … |
| `suite` | str | 套件名 |
| `difficulty` | str | `L1`–`L4` |
| `aliases` | str[] | 同一任务的口语说法，含中文 App 名，3–10 条 |
| `summary` | str | 一句话摘要（≤40 字） |
| `evidence_status` | str | `proven`=有成功轨迹；`unproven`=只有失败轨迹，内容为「怎么才可能做成」的推断 |

### 1.2 目标与前提（规划时先看这组）

```jsonc
{
  "goal": {
    "description": "任务目标原文",
    "success_criteria": ["判分字段 settings.general.fontSizeLevel 回读为标准档", "..."],
    "not_done_when": ["页面停在设置列表但滑块未动", "..."]
  },
  "preconditions": ["已登录支付宝", "网络可用且首页已加载", "..."],
  "entry": {"app": "alipay", "start_path": "/", "start_hint": "从「我的」底部 Tab 进入"}
}
```

- `success_criteria` 必须是**可观测证据**（判分字段、页面回读值、应用侧状态），不写「点完了」。
- `not_done_when` 是「看起来做完了其实没做成」的信号，用于执行期的自我否决。

### 1.3 判断点 / 陷阱 / 校验（执行时用这组）

```jsonc
{
  "decision_points": [
    {"trigger": "遇到什么信号", "thinking": "怎么判断、为什么", "options": ["路径A", "路径B"]}
  ],
  "pitfalls": [
    {"phenomenon": "上次真实踩过的现象", "cause": "原因", "avoid": "怎么避免"}
  ],
  "verification": ["完成后回读什么", "..."],
  "branches": [
    {"name": "做法名", "when": "适合什么情形", "approach": "怎么做"}
  ]
}
```

约定：
- `decision_points` 写「信号 → 判断 → 可选路径」，**不写第几步点哪里**。
- `pitfalls` 只来自失败轨迹或判分 `expected/actual` 差异；没有失败证据时为空数组（宁缺勿编）。
- 生成侧有质量闸门：拉丁乱码、把判分 expected 数值直接写进判断点/陷阱的条目会被丢弃。

### 1.4 溯源自检（审计用）

| 字段 | 说明 |
|---|---|
| `policy_version` / `active_policy_version` / `used_current_policy` | 该轨迹来自哪版策略；是否现役策略 |
| `generation` | 第几代 |
| `step_count` / `max_steps` | 实际步数 / 预算 |
| `judge_passed` | 是否判分通过（等于 `evidence_status == "proven"`） |
| `judge_checks` | `[{field, expected, actual, passed}]` |
| `episode_dir` | 轨迹目录，便于回溯截图 |
| `generated_at` / `updated_at` | 字符串时间 / 浮点时间戳（同步水位用 `updated_at`） |
| `progress` | `lifetime_attempts / best_steps / successes / cycle_attempts` |
| `reference_steps` | 参考动作序列（降级项，**不要当主体**） |
| `json_path` / `md_path` / `bytes` | 服务端落盘路径与体积 |

## 2. HTTP 接口

无鉴权，与现有 9817 面一致。

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/api/taskdocs` | 文档索引（只有元数据，无正文），`{count, schema_version, docs[]}` |
| GET | `/api/taskdoc/{task_id}` | 单份全文 JSON |
| GET | `/api/taskdoc/{task_id}/md` | 单份 Markdown（人读） |
| GET | `/api/taskdocs/search?q=&app=&top_k=` | 自然语言 → 相关文档候选 |
| GET | `/api/taskdocs/bundle` | 整包（离线检索用） |
| GET | `/api/taskdocs/sync?since=` | 按 `updated_at` 水位增量 |

### 2.1 检索接口

`q`：中文任务描述，必填；`app`：可选，`alipay` 或中文「支付宝」都行；`top_k`：默认 5，上限 20。

返回（每项只给规划需要的字段，正文按 `task_id` 再取）：

```jsonc
{
  "query": "帮我看看支付宝这个月花了多少",
  "app": null,
  "count": 3,
  "results": [
    {
      "task_id": "alipay.AnalyzeSpending",
      "task_name": "帮我看看支付宝这个月花了多少钱",
      "app": "alipay",
      "summary": "支付宝账单算最近5笔支出总额，切到答题卡填写并提交",
      "preconditions": ["支付宝已登录，能进入个人中心", "账单入口（我的-账单）可达"],
      "success_criteria": ["账单列表能读到最近5笔记录", "答题卡输入框已填入总额并提交"],
      "aliases": ["支付宝账单算最近5笔花多少钱", "..."],
      "evidence_status": "unproven",
      "score": 12.4,
      "matched_terms": ["账单", "支付", "花", "多少"]
    }
  ]
}
```

### 2.2 整包 / 增量

```jsonc
// GET /api/taskdocs/bundle
{"schema_version": 2, "server_time": 1793977638.0, "count": 39, "total_bytes": 219037, "docs": [ ... ]}

// GET /api/taskdocs/sync?since=1793977000
{"since": 1793977000.0, "server_time": 1793977638.0, "next_since": 1793977638.0,
 "count": 5, "total_bytes": 28573, "deleted": [], "docs": [ ... ]}
```

- `docs` 与单份全文同构，客户端按 `task_id` upsert。
- 下次请求带上 `next_since`（服务端时间，不是本地时间，避免时钟偏差）。
- 当前**没有删除语义**：文档只增/覆盖，`deleted` 恒为空。

## 3. 检索实现与选型

算法（`taskdoc.search`）：

1. 归一化：去标点、转小写；中文切 **CJK 二元组**，ASCII 按词切（含 `task_id` 的点分前缀）。
2. 打分：`sum(idf[t] for t in 命中词)`，IDF 只对**候选集**统计（有 `app` 过滤时只算该 App）。
3. 加成：完整短语命中 `+6`；别名命中 `+3`（纯 App 名如「支付宝」不算，避免同 App 文档雨露均沾）；指定 `app` 再 `+2`；`proven +0.6 / unproven -0.2`。
4. 排序：分数降序，同分按 `updated_at` 新者优先。

选型理由：
- 文档只有几十份、中文短查询、**没有向量库/embedding 依赖**；词袋 + IDF 在 39 份上实测 top-1 正确率满足需求，且完全可离线复刻到手机端。
- 线性扫描 39 份，服务端计算在**亚毫秒**级；实测 100 次 HTTP 往返（含网络与 JSON 序列化）均值 **13.7 ms**。
- 引入向量检索的代价（模型、维度、索引持久化）在这个量级不划算；`aliases` + App 归一化已经把「不同说法」覆盖掉，收益比换算法大。

实测样例（线上 39 份）：

| 查询 | top-1 | score |
|---|---|---|
| 帮我看看支付宝这个月花了多少 | `alipay.AnalyzeSpending` | 12.40 |
| 支付宝账单统计一下最近支出 | `alipay.AnalyzeSpending` | 18.09 |
| 把支付宝字体调大一点 | `alipay.SetFontSizeLevel` | 19.51 |
| B站看排行榜 | `bilibili.OpenRankingTask` | 6.64 |
| 帮我把铁路12306的密码改一下 | `account.Railway12306ChangePassword` | 22.11 |
| 在备忘录里新建一个待办 | `notes.CreateFolderAndMoveNote` | 22.85（top-2 为 `notes.CreateNewNote`） |

> 第 6 条说明：同一 App 内相近任务会一起返回，规划端应取 top-3 再按 `success_criteria` 自行判断，不要只看 top-1。

## 4. 同步与离线

数据量（实测）：39 份 / **219 KB** 整包，单份均值 **5.6 KB**。即使涨到 200 份也只有约 1.1 MB。

结论：**支持整包同步到设备本地做离线检索**，不需要「在线查 + 缓存兜底」作为主路径。

推荐策略：

1. 首次安装/换设备：`GET /api/taskdocs/bundle` 一次性落本地（219 KB）。
2. 之后每次联网：`GET /api/taskdocs/sync?since=<last next_since>`；只拿 `updated_at` 变过的文档，按 `task_id` upsert。
3. 本地检索：把 `taskdoc.search` 的同一套规则在端上复刻（CJK 二元组 + IDF + 别名/App 加成）。IDF 用本地全集现算，保证与在线一致；也可以把 `_tokens()` 结果预计算进本地索引，命中更快。
4. 离线退化：
   - 有本地包 → 检索、取全文全部走本地，行为与在线一致；
   - 无本地包且离线 → 返回空候选，由 Agent 走通用探索流程（不要伪造文档）；
   - 在线可用但本地包过期 → 在线结果优先，同时后台跑增量同步刷新本地。

注意：`updated_at` 是**服务端时间**；手机时钟不准时，必须以服务端返回的 `next_since` 为准，不要用本地 `now()`。

---

## 5. 手机端接入点（规划 / 执行）

- **规划时**：把用户目标原文喂 `search(q, app=当前App, top_k=3)`，拿 `summary + preconditions + success_criteria` 做任务分解与可行性判断；`evidence_status == "unproven"` 的文档只当「参考思路」，不作为可行性证明。
- **执行中**：按选中的 `task_id` 取全文，`decision_points` 用于每步遇到异常时分支判断，`pitfalls` 用于避免重蹈失败轨迹，`verification` 用于结束前自检；`reference_steps` 只在卡住时参考，不要逐步照抄坐标。
- **收尾**：用 `goal.success_criteria` + `verification` 逐条回读，全部满足才算完成；`not_done_when` 命中即判定未完成。
