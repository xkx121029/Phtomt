### 4.1 回滚验证：v25/v26 的真实记录与「假晋级」修正

线上策略库 27 版，`active=26`。v13–v24 的 verdict 全部是「同分（且无效率优势），保持现役」，验证集只有 1 题（如 v24 的 `tasks=["alipay.AnalyzeSpending"]`）——这就是用户说的死锁。

v25（新代码第一次跑）：
```
sr_old=0.0 sr_new=0.0 steps_old=15.0 steps_new=0.0 verdict=同分（且无效率优势），保持现役
```
v26（第一次晋级）：
```
sr_old=0.0 sr_new=0.0 steps_old=12.33 steps_new=0.0
progress_old=0.1667 progress_new=0.0
false_complete_old=0.3333 false_complete_new=0.0
verdict=同分但次级指标更优（progress/假完成/步数）
tasks=alipay.CheckBalance alipay.CheckDailyIncome account.Railway12306ChangePassword
      account.Railway12306ForgotPasswordReset account.Railway12306RegisterThenLogin alipay.EnableDarkMode
```
- 6 题跨难度验证集确实生效（跨 alipay/account 两个套件、任务难度混合），**死锁的机制被打破是真的**；
- 但 `steps_new=0.0` 说明 new 侧**没有一个 episode 真正跑起来**：0 步样本进了分母，`false_complete_new` 仍是 0.0，于是「假完成更少」被误判为更优。
- 根因（**次日对方复核后修正**）：不是「new 侧结果为空」那么简单，而是 **0 步的 ERROR episode 被算进了分母**——0 步既没有动作也没有假完成，于是 `false_complete_new=0.0` 天然小于旧的 0.3333，被判成「更优」。换句话说，**分母污染**让「什么都不做」成了最优解。
- 结论：v26 是**基于 0 步样本的假晋级**，不能算作「验证集改造有效」的正面证据；机制修复成立、首次判决不成立。

**补丁 A（已部署，22:40 第一次）**：任一侧 episode 数不足即保持现役。
**补丁 B（已部署，00:03）**：新增 `_usable()` 统计口径——
1. `error is not None` 的 episode 一律剔除；
2. `steps <= 0` 的 episode 一律剔除（含 0 步 ERROR）；
3. `stop_reason == ERROR` 一律剔除；
4. 每侧有效样本 `< max(2, 计划数/2)` 即判「有效样本不足，保持现役」；

### 6.3 客户端归因的结构化字段（已实施，2026-11-04）

**现状（改前）**：客户端靠「ERROR 占比 ≥60%」或 `last_error` 含 `429/quota/配额/限流` 来推断（`web/summary.html:549-552`，Android 侧同逻辑），字符串匹配会把 `TimeoutError`、`judge_error` 一并卷进来。

**已实施**：`config.py` 的 `RuntimeState.snapshot()` 新增 5 个键（经 `/api/health` 的 `state` 返回），**只增不改，原有 key 一个未动**：

| 字段 | 类型 | 取值 | 计算口径 |
|---|---|---|---|
| `error_kind` | string | `none` / `quota` / `judge` / `env` / `model` / `unknown` | 最近一次 **ERROR** episode 的归因（可「粘住」：之后成功了也保留上次错误类型）；窗口内从未出错 → `none` |
| `quota_limited` | bool | `true` / `false` | 最近 20 个 episode 内是否出现 429/配额/限流类错误 |
| `error_rate_recent` | float | 0–1 | 最近 N 个 episode 中 ERROR 占比；N = 已记录条数（≤20）；无记录时 0.0 |
| `recent_episodes` | int | `20` | 窗口容量（固定值，不是实际条数） |
| `guard` | object | `{"checks": int, "blocked": int, "checks_message": int, "blocked_message": int}` | 回执守卫进程内累计（两个层各一组）：checks/blocked=答题卡与 answer 层，checks_message/blocked_message=agent_message 层；**容器重启清零，不是历史拦截总数** |

分类关键词（按顺序命中即返回）：`quota` ← 429 / rate limit / quota / 配额 / 额度 / 限流 / too many requests / insufficient；`judge` ← judge / vlm / 判分；`env` ← sim / environment / env_error / adb / emulator / 环境；`model` ← timeout / llm_error / connection / upstream / 502 / 503 / 504 / 模型；其余 `unknown`。

**兼容性与限制**：只新增字段，老客户端缺字段时退回原推断逻辑即可；窗口只在内存中维护，**容器重启后清零**，所以不要把它当历史统计（历史仍看 `history`/`events`）。成功 episode 记为 `ok`，不参与错误率分子；容器内冒烟验证：`['429…','TimeoutError…','judge_error…','TypeError…',None]` → `['quota','model','judge','unknown','none']`，三集（配额/超时/成功）→ `error_kind=model`、`quota_limited=true`、`error_rate_recent=0.6667`。

## 14. 收尾校验（complete_verify）与假完成成因归因（2026-11-08）

### 14.1 收尾校验冒烟：拦截 0 次，按规则停下

实现按批准口径落地：第 1 次 COMPLETE 只回读不结束；第 2 次判提交回执，不成立拦一次；第 3 次无条件放行。回执分两支——答题类读 `obs.state["apps"]["answer_sheet"]` 的 `submitted` + `answers`（**不能读 `task.apps`**，那里面从来没有 answer_sheet）；非答题类用 `task.resolve_expected_paths()` + `StateComparator.diff_states()` 判「预期状态是否真的变过」。最后一步也做校验，但只记录不拦截（没有下一步可走，拦了等于判死）。

冒烟 5 任务 × 2 臂 = 10 集（sms.CompareConversationMessageCount / sms.ReadUnreadConversationCount / notes.DeleteTodo / spotify.QueueAndLikeSong / wechat.SetSignature）：

| 指标 | 关 | 开 |
| --- | --- | --- |
| 成功率 | 1/5 | 1/5 |
| 假完成 | 3/5 | 3/5 |
| `complete_receipt_blocks` | 0 | **0** |
| 回执校验执行 | — | 4 次 |

四次校验全部返回「通过」：`answer_sheet_submitted -> submitted=True, answers=1` ×2、`ok -> 3 diffs matched`、`ok -> 1 diffs matched`。`complete_receipt_kind` 四类计数：answer_sheet_submitted 2、state_unchanged 0、no_expected_declared 0、ok 2。

**结论：这批假完成的提交回执都是真的。** 答题卡确实提交了、预期状态确实变了，判分不过是因为**答案内容错**（填了看起来合理的值）或**操作对象错**，不是「点了没生效」。提交回执这个判据在语义上抓不到它，继续加严只能变成「把判分器复制进循环」。

按预设规则（`complete_receipt_blocks == 0` 就停）**64 集全量对照没有开跑**。`complete_verify` 开关保持关闭，代码保留可回溯。

### 14.2 一次被吞掉的异常（本轮最大发现）

冒烟前三轮（v2/v3/v4/v5）一直显示「答题卡读不到、apps 为空」。真因是 `Controller.run` 里原本有一行局部 `from dataclasses import replace as dc_replace`：Python 因此把 `dc_replace` 视为整个函数的局部变量，我在 COMPLETE 处提前引用就抛 `UnboundLocalError`，又被外层的 `except Exception` 兜成「放行」。于是**校验压根没跑，却每次都打印「通过」**。

这类问题比归因结论更重要，因为它会让任何「前置条件命中 0」看起来像「数据如此」。本轮已修（删掉局部 import，改用顶层引用），并把回执判定失败的原因写进 detail / 日志，不再静默。

### 14.5 判分口径复核（G 桶，7 次）

`spotify.QueueAndLikeSong` 的 `expected_changes` 只写了 `["queue", "likedSongs", "searchHistory"]`，而同套件兄弟任务（如 `QueueSongsFromSearch`）写的是 `["queue", "currentTrack", "currentTrack.cover", "isPlaying", "recentPlays", "playHistory", "searchHistory"]`。这个模拟器里「加到播放队列」会立刻开始播放，`currentTrack / isPlaying / recentPlays / playHistory` 的变化是必然副作用，不是模型的额外动作。于是 7 集目标全达成却被判失败。

影响：这 7 集把成功率低估了 3.5pp（7/200），同时把假完成率高估了同样的量。**这是任务文档的一行缺陷，不是判分器逻辑错误**，修法是把缺的路径补进 `expected_changes`。

另有两处「可疑但未确认」，单列待查：

1. `reddit` 5 例：模型自称「点赞数变为 1494」，但 `new_upvotes` 为空。可能是模型点在了**已点赞**的评论上（再点变成取消），也可能是投票没落到该 store。需要看步级截图才能定，不列入判分口径问题。
2. `spotify.DiscoverSaveAndReport` 1 例：模型最后一句出现「答题卡APP中已填写温差城市为北京，会议数量为0」——这两个字段属于天气/会议任务。怀疑答题卡注入用 `reload=False`，上一集留下的题面在页面刷新前仍可见（跨集残留），属静默失败候选。

### 14.6 结论：最值得修的是哪一层

1. **先修 G（任务文档，一行）**：成本最低、不改变模型行为，直接把 7 集从失败改判为成功，让基线干净。改动点：`bench_env/task/spotify/tasks.py` 的 `QueueAndLikeSong.expected_changes` 补齐播放副作用路径。
2. **大头是 A+B+C（28 次，45.2%）**：全是「读数类」任务——比两个会话谁消息多、数未读会话、读指定便签内容。模型不是没做操作，是**读错了对象或数错了数**。这一层不在判分器、也不在任务文档，而在**提示词 + 交互流程**：要求把读到的原文/计数先逐条写出来（每读一个会话记一行），再比较、再填答题卡；`complete_verify` 的回读提示对这类无效（回执是真的）。
3. **E（14 次，22.6%）**：操作后没有验证结果态，模型以「我点了」当完成。修在提示词层：要求「点击后必须看到目标状态变化（列表出现条目/按钮变色/计数变化）才算完成」。reddit 那 5 例还需要先确认是不是「点在已点赞的评论上」。
4. **D（8 次，12.9%）**：输入框是追加语义，模型不知道要先清空。最小改动在**工具语义层**（TYPE 前清空或提供 replace），比提示词可靠。
5. **F（3 次）**：提示词层要求删前核对列表，量小优先级低。

## 15. 预算记账：测量消耗了被测资源（2026-11-09，已部署）

和「键在值空」「坏了但不响」并列的第三类：**账本身是错的，而且错得很安静**。

### 15.1 现象

`/api/health` 的 `episodes_done` 同一天出现 312 → 302 → 297 三个数，`updated_at` 却停在上一轮。没有人改状态快照，是计数口径本身有两个缺陷：

1. `_run_episode_for_policy` 是所有 episode 的公共出口，**定向验证（`eval_tasks`）和训练内 A/B 验证都走它**，末尾无条件 `episodes_done += 1`。于是「测量」在消耗「被测量的预算」。
2. 同一个计数既当训练进度又当评测次数：`episodes_done` 只在内存里加，**定向验证从不落盘**，重启时从 `history.json` 重算，多出来的部分直接蒸发。

### 15.2 对账（可一眼验）

`history.json` 40 代：训练 `episodes` 合计 **122**，A/B 验证 `val_episodes` 合计 **175**，122 + 175 = **297**，与旧口径重启后的读数完全一致。

| 读数 | 旧口径构成 | 新口径拆法（训练 + 验证） |
| --- | --- | --- |
| 297（重启后） | 122 + 175 | 122 + 175 |
| 312（跑完 3 任务 × 5 集基线后） | 297 + 15 | 122 + 190 |
| 302（跑完 B1 5 集后重启） | 297 + 5 | 122 + 180 |
| 303（再跑 1 + 5 集后） | 297 + 6 | 122 + 181 |

那 15 / 5 / 6 是定向验证，旧实现只加在内存、不写任何账本，所以每次重启都回落到 297。**历史 `history.json` 不回写**（它是事实记录），新口径从 2026-11-09 起生效。

### 15.3 改动

- `episodes_done` 只累计训练集；`is_eval=True` 的调用改记 `eval_episodes_done`。
- 新增 `/data/eval_log.json`：一条记录 = 一集，字段 `ts / tag / task_id / trial / episodes`，`total` 单调累加，`records` 保留最近 500 条；不塞进 `history.json` 假装是训练代。
- 启动重算：训练数从 `history.json` 的 `episodes`，验证数从 `history.val_episodes` + `eval_log.json`。
- `/api/health` 两个数都出；`budget_note` 写成「已完成 122（训练集；另有验证 175 集不占预算）」。
- 训练内 A/B 的 `val_episodes` 改从独立计数器差值取，不再用 `episodes_done` 差值反推。

部署后实测：`episodes_done=122`、`eval_episodes_done=175`、`paused=true`，训练未恢复。

### 15.4 一句话原则

**测量不许改变被测对象。** 计数器同时承担「训练进度」和「评测次数」，就等于让验证动作吃掉训练预算，还会在重启时凭空蒸发。

## 16. 环境闸门换判据 + 环境懒启动（2026-11-10，已部署）

### 16.1 为什么换：`load<1.0` 从一开始就选错了代理

旧闸门要求「宿主 load(1min) < 1.0 连续两次」。它真正想保证的只有一件事：**本轮和上一轮环境大致可比**。而上一轮（B1 3/5 那轮）实际量到的是 **per_step 4.7–6.9s**。宿主上还常驻别的项目，load 地板就在 2.4–3（11-09 夜间最低 2.45），`load<1.0` 这个数字几乎永远不会出现 —— 等于拿一把永远指不到 0 的尺子量东西。11-09 23:06–23:19 的记录就是空等：`load` 6.86 / 10.01 / 9.93 / 10.32，`streak=0/2`。

> **更正（2026-11-10，作废上面那句里的「load 地板」判断）**
>
> 「整机地板 2.4–3（最低 2.45）」应降级为**「未排除自污染因素的初步观察」**，不能再当作
> 机器能力的结论。理由是当天的取证（详见 `PROBES.md` 的「自污染更正」）：
>
> 1. 五轮校准里 `load1` 是 4.93 → 1.48 → 2.33 → 2.35 → 1.25（**下降**），
>    `trainer_cpu_cores=0.00–0.04`（我们自己是闲的），而 `per_step` 却是
>    19.53 → 11.57 → 12.79 → 16.16 → 16.50。两个方向不一致，「机器累坏了」解释不通；
> 2. 2026-11-10 01:06 误跑第二个探针 loop，两个浏览器叠加 → 当轮轻探针
>    `12.75s / elements1 9.3s / mem 1146.9MB`；杀掉多余 loop 后立刻回到
>    6.30s → 6.02s → 5.20s，`mem` 回到 1427MB。**多一个我们自己漏掉的浏览器，
>    下一次测量就翻倍**；
> 3. 所以此前说的「机器慢了两三倍」，正确表述是「**至少相当一部分是我们自己的测量
>    进程没收干净导致的自污染**」。历史逐轮浏览器数因容器三次 force-recreate 已不可恢复，
>    这里只报能复原的数据。
>
> 同时更正口径：`per_step = runtime_s / steps` 里含 LLM 推理时间，**它不是机器速度**
> （01:30 重探针 27.24s/步、`tokens=67532`；同轮轻探针纯浏览器只有 5.2–7.5s）。
> 因此 `STEP_MAX=7.0s` 对本环境不可达，后续门应改用 `stopwatch` 的机器侧分段。

换成 per_step 不是放宽，是**更严**：

- 旧判据：load 低、但机器在抖（别的项目短时抢占）也能进；
- 新判据：必须真跑校准集、量出每步墙钟才放行。

### 16.2 新判据（`scripts/gate_eval.py`，容器内运行）

1. 训练必须 `paused`（不抢环境）；
2. **trainer 自身 CPU 基线 ≤ 0.5 核**（读 cgroup v2 `/sys/fs/cgroup/cpu.stat` 的 `usage_usec`，8s 差分）。paused 时应 0.1–0.2 核；异常高说明吃 CPU 的是我们自己的东西，先拦；
3. 校准集跑 **2 次**，`per_step = runtime_s / steps` 取**中位 ≤ 7.0s**；同时从每集 `trajectory/**/step_00N.jpg` 的 mtime 差，算出单集内每步 **p50 / p90**，不只看一个均值；
4. `load(1min)` 只记录、不再作为门槛。

每次输出（评测报告也照抄这一行）：

```
环境：per_step=X s，整机 load=Y，与上一轮不严格等价
```

含义是**环境近似、不可完全比拟**：前后两轮的数字不许直接相减。

`watch_b1.py` / `watch_gate_chain.py` 已同步删掉 `LOAD_MAX` / `wait_gate()`，改走同一套判据；慢只算本轮环境结论，冷却 10 分钟再测，**最多 6 次**（每次 2 集），不空烧 episode。

### 16.3 懒启动与它的对称面

- `boot()` 原来无条件 `MobileGymEnv(...).start()`：**paused 也拉一个 Chromium 空转**。实测 paused 时容器自身 CPU **0.64 核**，正是闸门第 2 条要拦的那种「我们自己的问题」。
- 现在 `boot()` 只做静态服务检查 + 目录/账目加载，环境由 `_ensure_env()` 在**首个 episode 前**拉起；已启动实例复用，不每集重建；用 `asyncio.Lock` 防止训练与定向验证并发拉两个浏览器。
- 5 个评测/对照入口（`eval_tasks` / `ab_step_budget` / `ab_screen_gate` / `ab_complete_verify` / `ab_text_first`）不再在 `env is None` 时直接返回「环境未就绪」，改为按需拉起。
- `_delayed_restart` 原来自愈靠 `await boot()`；懒启动后那条路会直接 return 把主循环停死，已改成 `_ensure_env("主循环自愈")`。
- 对称面 `release_env_if_idle()`：评测/对照跑完、训练仍 paused 时主动关浏览器（API 5 个 `finally` 里调用）。否则 B1 跑完浏览器一直温着 0.64 核，下一项评测会被闸门第 2 条拦住。

实测 CPU 基线：`0.64 → 0.02 → 0.00` 核（改前 / 改后两次重建）。

### 17.5 仪表两条新规矩（2026-11-10 立）

1. **所有计数器必须落盘**：只在内存里的计数视为「重启即失效」，报告里不允许引用跨重启累计值。
   `swallowed` 已改为追加写 `/data/swallowed.jsonl`（每行 `{ts, site, exc_type, msg, note}`），
   读取走 `/api/swallowed?limit=N`，只回看文件尾部（64KB 分块、上限 8MB），不做全量扫描；
   落盘失败会 `logger.error` 并计入 `write_errors`。
2. **`unjudged` ≠ `env_error`**：前者是「秤没跑」（必须告警），后者是「环境崩了」（算环境账）；
   两者都不进成功率分子/分母，但必须分开计数，报告里出现时必须带定义。

另加**机会式排期的停机规则**：连续 3 小时开不出一批（一直被 PSI 窗口或门禁拦下）→ 直接停，
报告「今天宿主压力全程不合格」，附每 10 分钟一个点的 PSI 时间序列（`host_unfit.md`）；
不允许空转一整天还假装在工作。详见 `PROBES.md`「机会式排期」。
