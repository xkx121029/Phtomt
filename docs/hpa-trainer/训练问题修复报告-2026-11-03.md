### 4.1 回滚验证：v25/v26 的真实记录与「假晋级」修正

线上策略库 27 版，`active=26`。v13–v24 的 verdict 全部是「同分（且无效率优势），保持现役」，验证集只有 1 题（如 v24 的 `tasks=["alipay.AnalyzeSpending"]`）——这就是用户说的死锁。

v25（新代码第一次跑）：
```
sr_old=0.0 sr_new=0.0 steps_old=15.0 steps_new=0.0 verdict=同分（且无效率优势），保持现役
```
v26（第一次晋级）：
```
sr_old=0.0 sr_new=0.0 steps_old=12.33 steps_new=0.0
progress_old=0.1667 progress_new=0.0
false_complete_old=0.3333 false_complete_new=0.0
verdict=同分但次级指标更优（progress/假完成/步数）
tasks=alipay.CheckBalance alipay.CheckDailyIncome account.Railway12306ChangePassword
      account.Railway12306ForgotPasswordReset account.Railway12306RegisterThenLogin alipay.EnableDarkMode
```
- 6 题跨难度验证集确实生效（跨 alipay/account 两个套件、任务难度混合），**死锁的机制被打破是真的**；
- 但 `steps_new=0.0` 说明 new 侧**没有一个 episode 真正跑起来**：0 步样本进了分母，`false_complete_new` 仍是 0.0，于是「假完成更少」被误判为更优。
- 根因（**次日对方复核后修正**）：不是「new 侧结果为空」那么简单，而是 **0 步的 ERROR episode 被算进了分母**——0 步既没有动作也没有假完成，于是 `false_complete_new=0.0` 天然小于旧的 0.3333，被判成「更优」。换句话说，**分母污染**让「什么都不做」成了最优解。
- 结论：v26 是**基于 0 步样本的假晋级**，不能算作「验证集改造有效」的正面证据；机制修复成立、首次判决不成立。

**补丁 A（已部署，22:40 第一次）**：任一侧 episode 数不足即保持现役。
**补丁 B（已部署，00:03）**：新增 `_usable()` 统计口径——
1. `error is not None` 的 episode 一律剔除；
2. `steps <= 0` 的 episode 一律剔除（含 0 步 ERROR）；
3. `stop_reason == ERROR` 一律剔除；
4. 每侧有效样本 `< max(2, 计划数/2)` 即判「有效样本不足，保持现役」；
5. `validation` 新增 `dropped_old / dropped_new / valid_old / valid_new / planned`，剔除量可审计。
首次带 `dropped_*` 字段的真实判决见 §4.6（两侧各 6/6 有效、dropped=0）。

### 6.3 客户端归因的结构化字段（已实施，2026-11-04）

**现状（改前）**：客户端靠「ERROR 占比 ≥60%」或 `last_error` 含 `429/quota/配额/限流` 来推断（`web/summary.html:549-552`，Android 侧同逻辑），字符串匹配会把 `TimeoutError`、`judge_error` 一并卷进来。

**已实施**：`config.py` 的 `RuntimeState.snapshot()` 新增 5 个键（经 `/api/health` 的 `state` 返回），**只增不改，原有 key 一个未动**：

| 字段 | 类型 | 取值 | 计算口径 |
|---|---|---|---|
| `error_kind` | string | `none` / `quota` / `judge` / `env` / `model` / `unknown` | 最近一次 **ERROR** episode 的归因（可「粘住」：之后成功了也保留上次错误类型）；窗口内从未出错 → `none` |
| `quota_limited` | bool | `true` / `false` | 最近 20 个 episode 内是否出现 429/配额/限流类错误 |
| `error_rate_recent` | float | 0–1 | 最近 N 个 episode 中 ERROR 占比；N = 已记录条数（≤20）；无记录时 0.0 |
| `recent_episodes` | int | `20` | 窗口容量（固定值，不是实际条数） |
| `guard` | object | `{"checks": int, "blocked": int, "checks_message": int, "blocked_message": int}` | 回执守卫进程内累计（两个层各一组）：checks/blocked=答题卡与 answer 层，checks_message/blocked_message=agent_message 层；**容器重启清零，不是历史拦截总数** |

分类关键词（按顺序命中即返回）：`quota` ← 429 / rate limit / quota / 配额 / 额度 / 限流 / too many requests / insufficient；`judge` ← judge / vlm / 判分；`env` ← sim / environment / env_error / adb / emulator / 环境；`model` ← timeout / llm_error / connection / upstream / 502 / 503 / 504 / 模型；其余 `unknown`。

**兼容性与限制**：只新增字段，老客户端缺字段时退回原推断逻辑即可；窗口只在内存中维护，**容器重启后清零**，所以不要把它当历史统计（历史仍看 `history`/`events`）。成功 episode 记为 `ok`，不参与错误率分子；容器内冒烟验证：`['429…','TimeoutError…','judge_error…','TypeError…',None]` → `['quota','model','judge','unknown','none']`，三集（配额/超时/成功）→ `error_kind=model`、`quota_limited=true`、`error_rate_recent=0.6667`。
