> 一款运行在 Android 手机上的 AI 智能体：一句话下任务，手机自己看懂屏幕、规划步骤、动手点完；同时自带一整套设备内开发环境，能在手机里写完代码直接打出 APK。

## 一、核心功能与亮点

先给结论：这个作品解决的不是「让 AI 聊天」，而是**让 AI 在一个真实、脆弱、充满厂商定制的手机系统上，把有副作用的事做完并证明做完了**。下面是已经跑通、且在真机上验证过的五项主功能。

### 1. 一句话跨 App 执行：从「说目标」到「屏幕上真发生」

**帮用户完成什么**：把「打开相册找最近一张照片」「设一个 10 分钟后的闹钟」「查大连今天气温」「启动 5 分钟计时器再打开日历看今天日期」这类跨 App、多步骤的琐事，压缩成一句话。用户不需要知道哪个 App 在哪个入口、哪个按钮叫什么。

**怎么实现的**（不是一句话调个大模型那么简单）：

- **ReAct 主循环**：`观察 → 广告过滤 → 敏感页判定 → 页面记忆 → 宏接力 → 端侧/云端决策 → 技能归一化 → 动作模式门控 → 浏览器分流 → 意图转译 → 带验证执行 → 留痕`。每一步都有明确的单一定义点，不是散落在各处的 if。
- **AI 只说「做什么」，不说「怎么做」**：意图 65 个，由端侧 `IntentTranslator` 的策略表落到 38 种 `ActionType`。AI **不输出 shell 命令、不输出像素坐标、不选执行通道**——换模型、换通道、换分辨率都不用改提示词。
- **语义 ID 定位**：每次观察后为 26 类常见控件分配稳定 id（`send_btn` / `dlg_allow` / `ad_skip` / `checkout_btn`…），AI 说「点 send_btn」，端侧自己去找元素。坐标会漂，语义不会。
- **带验证执行**：动作执行前后比对页面指纹，把「操作已交付」和「操作真生效」分开。页面已出现完成证据时跳过重复副作用（提交 / 发送 / 下单 / 支付 / 删除），防重复下单比事后道歉便宜得多。

**相比原有方式的改进**：

| 原有方式 | 现在 | 改进点 |
| --- | --- | --- |
| 用户手动跨 2–3 个 App 点十几到几十下 | 一句话 + 一次计划批准 | 真机实测：5 步跨 App 任务平均 18 步执行、约 8 分钟无人值守完成，中途误入页面还能自行纠错退出 |
| 传统自动化脚本（坐标写死、App 一改版即失效） | 语义 ID + 页面指纹 + 模板复用 | 换皮肤、换分辨率、换机型不需要重写脚本 |
| 「AI 说完成了」不可信 | 完成判定必须带页面证据，否则不许 finish | 实测 5 个成功任务全部有证据复核，无虚假完成 |

### 2. 三形态路由 + 端侧快速决策：不拿云端额度去买单弹窗

**帮用户完成什么**：同一条输入框，既能操控手机，也能写代码，也能纯聊天；并且高频琐碎页面（弹窗、加载中、开屏广告）在本地就处理掉，用户不用等一次云端往返。

**怎么实现的**：

- 每次输入先过 `TaskKindDetector` 判形态：**Coding**（编码词命中数 ≥ 对话词与操作词）→ 委托设备端编码 agent；**Chat**（只命中对话词）→ 主模型直答一次，不注入操控提示词；**Agent** → 进 ReAct 主循环。判定器同时决定提示词怎么裁块，不会「按网页任务裁」和「按普通任务注入」两套口径打架。
- `LocalDecisionEngine` 先处理弹窗 / 加载 / 广告这类高频页面，**连续 5 次端侧决策强制走一次云端复核**——本地负责省钱和快，云端负责兜住「本地看不出来」的情况。
- 视觉按需分流：端侧 3B（Qwen2.5-VL GGUF + JNI）→ 云端视觉 → ML Kit 中文 OCR 三级兜底；页面复杂度按「元素树稀疏度」判定（`elements ≤ 3` 视为无障碍读不到控件，才值得上云端）。
- 视觉结果按「页面指纹 + 截图尺寸 + 任务 ID」缓存复用，同一页面连续步骤整段跳过三路调用。

**相比原有方式的改进**：一次任务里真正花钱的云端调用被压到「需要语义理解的步」，其余在端侧闭环；用户侧感知是「点了就有反应」，而不是每一步都转圈。

### 3. 三档动作授权 + 安全防护：让用户敢把手机交出去

**帮用户完成什么**：把「AI 能做什么」的授权粒度交给用户，而不是二选一「全开 / 全关」。

- 动作模式与执行通道**正交**：通道模式回答「设备有没有权限」，动作模式回答「允不允许 AI 提这类请求」。保守档放行 35 项低风险意图，均衡档（默认）放行 61 项，自由档才开放 AI 自写命令、命令行、虚拟屏与 18 个无障碍端点直调（共 65 项）。
- 门控点全项目只有一处（技能归一化之后、浏览器分流之前），刻意卡在这里才能把不走转译层的 `browse_*` 一并盖住；连续 3 次被拒即收尾并提示放宽档位，不无限重试。
- 安全四件套：敏感页只读（支付 / 密码 / 验证码关键词，连续 5 次接管仍敏感即收尾）、数据脱敏（身份证 → 银行卡 → 手机号按长度降序掩码）、不可逆动作强制二次确认（120 秒超时视为取消）、密钥加密后落 DataStore。

**相比原有方式的改进**：自动化工具的通病是「要么什么都不敢做，要么一路横冲直撞」。分档位 + 单点门控 + 强制确认，让「第一次用」和「老手放权」是同一个产品。

### 4. 设备内编码环境：在手机里 `assembleDebug`

**帮用户完成什么**：出门在外只有手机，发现线上 bug 要改一行、要验一次构建——不用回电脑，手机里就能跑通「写代码 → 编译 → 出 APK」。

- `env` 是独立 APK（targetSdk 固定 **28**），承载 PRoot + Alpine 根文件系统；主应用经 `IEnvProvider` AIDL 远程驱动，自己完全不碰系统权限代码。
- 整条链路固化成幂等状态机：`探测 → 装组件 → 全文件访问 → 组件存储授权 → Linux 根 → JDK 17 → Gradle → cmdline-tools → platform / build-tools → aapt2 兼容层 → assembleDebug`。每次调用只推进到**第一个需要用户动手的环节**并拉起对应系统页面，返回 `needsUserAction`，用户办完重跑，做完的步骤不重复。
- 工程版本不用手填：优先读 `gradle-wrapper.properties` 的 `distributionUrl`，没有 wrapper 时按 AGP 版本查官方配套表（8.0–9.4 全覆盖）。
- 编码 Agent 与操控链路**彻底隔离**：独立会话、独立工作区、独立状态目录（`<工作区>/.happyac/agent`），切工作区即切一整套记忆。随包 Node 宿主启动时把系统 CA 拼进 `NODE_EXTRA_CA_CERTS`，让 Node 与 OkHttp 的信任面一致。

**相比原有方式的改进**：云 IDE 断网即废、代码还要传上去；这套工具链全在设备本地，随时可编译。这是「手机智能体」和「远程 IDE 客户端」的分界线。

### 5. 记忆体系 + 长任务稳定性：越用越快，不跑偏

**帮用户完成什么**：让长任务在几十分钟、几十步之后仍然朝着目标走，而不是在第 20 步开始胡乱点。

- **页面记忆**：把控件空间树 + 热点画成纯线框的虚拟手机画面（不存截图，不占空间也不泄露内容），屏幕上用淡色圆环标记已记忆控件，决策时注入「这个页面可以从哪里去哪里」。
- **经验沉淀**：真机实测中，AI 自己学会了「手电筒可以用语音助手指令」「相册主界面按时间排列」，跨任务复用——原本要 5 步找控件的任务，第二次 1 步直达。
- **防线**：决策异常不计步（`step--` 重试，避免网络抖动烧光步数预算）、连续 5 次异常才收尾；中途无障碍被厂商安全守护清掉立即暂停并引导重授权，不进入盲循环；任务记忆 + 检查点 + 熔断计数 + 模板复用。
- 提示词按任务裁切：60 个区块带装配条件，铁律 / 授权范围 / 禁止输出 / 能力声明**永不裁**，非网页任务省掉「网页浏览」块——同样一次决策，少喂几千 token。

**相比原有方式的改进**：真机实测的复合长任务（跨 2 App、18 步、约 8 分钟）能跑完并逐步汇报；这一点在纯 ReAct 实现里通常会崩在第 10 步左右。

## 二、TRAE 在开发过程中的具体帮助

说明一下分工：**方向、架构边界与验收标准由我定，TRAE 负责把判断落到代码与验证上**——读全项目、定位、改造、跑编译与单测、写文档、执行构建与发布。下面是三个对作品有实质贡献的任务。

### 任务 A：把「手机里 build APK」从不可行变成可用

**当时要解决的问题**：想让 App 具备设备内编码能力，卡在四个硬约束上——

1. Android 10+ 的 W^X 只允许 `targetSdk < 29` 的应用 `execve` 私有目录下的程序，主应用（targetSdk 36）根本执行不了任何自带二进制；
2. 环境组件是另一个 uid，读不到主应用 `filesDir`，工程目录放哪都别扭；
3. `aapt2` 只有 x86_64 版本，主流手机是 arm64；
4. 用户不可能手动敲 8 步命令装 JDK + Gradle + SDK。

**我的判断**：不做自研打包链路，直接复用 PRoot + Alpine 这套成熟生态；不在主应用里硬塞 Linux 环境，而是拆成独立 `env` APK + AIDL 跨进程契约；不追求「一条命令装完」，而是承认用户必须点几次系统授权，把流程做成**可中断、可续跑的状态机**。

**TRAE 具体做了什么**：

- 把整条 bootstrap 写成 `CodingEnvBootstrap` 的幂等状态机，每步失败只返回 `needsUserAction` 而不是抛异常——这是「用户去开个权限回来接着跑」能成立的前提；
- 处理 arm64 的 aapt2：用 `qemu-x86_64` + glibc 转译执行，把兼容层作为流程里的显式一环，而不是事后打补丁；
- 解决跨 uid 目录问题：私有工作区在构建前镜像到 `/storage/emulated/0/happyac-build/<工程名>`；
- 解析工程版本：wrapper 优先、无 wrapper 时按 AGP 8.0–9.4 官方配套表推导，`compileSdk` / `buildToolsVersion` 从模块脚本读；
- 建立 `env-api` 模块的 AIDL 契约（`IEnvProvider` / `IEnvCallback`）与 `HostBridgeServer` 的 `env_status` / `env_setup` / `env_build` / `env_cancel` 四个桥方法。

**最终体现**：手机端可以真正跑 `assembleDebug` 出 APK，README 里有完整的「探测 → … → assembleDebug」流程图，这条能力也成了作品区别于纯云端方案的核心卖点。

### 任务 B：全项目架构审计与统一性收口（2026-10-24）

**当时要解决的问题**：代码涨到 261 个文件后，出现典型的「能跑但越改越怕」——同一件事有多个定义点、分层出现反向依赖、日志两套系统并存，改一处不知道会崩哪。

**我的判断**：不推倒重来。先做**只读审计**把所有违规定位到文件行号，再按「行为等价」原则逐项修，每一步都用编译 + 全量单测验证，绝不把重构和功能改动混在一个提交里。

**TRAE 具体做了什么**：

- 四轮定向扫描（包依赖方向、设计令牌、DI、并发、日志、常量、序列化、资源、生命周期、Manifest），产出带行号的发现清单；
- 修掉两处反向依赖：`core → ui`（`TaskProgressNotifier` 改经 `PackageManager` 取启动意图）、`domain → engine`（`effectiveLabel` 下沉为 `domain/rules/PageTypeRules.kt` 纯函数）；
- 收口「回注预算 4000」的 4 个定义点 → `core/AgentBudgets.REINJECT_MAX_CHARS` 单一数值源；
- 日志双轨 11 个文件 → `core/log/AppLog.kt` 门面 + sink 钩子，调试页重新可见；
- 圆角 16 处硬编码 → `AppRadii` 令牌，视觉零变化；
- 34 个测试文件 `git mv` 对齐新包结构，删掉 11 个空目录，66 个测试文件 package 与目录 100% 一致；
- 验证：`compileDebugKotlin` ✅、`testDebugUnitTest` ✅ 全绿后才落提交。

**最终体现**：产出 `架构统一性审计报告.md`（带 ✅/⏸/⛔ 状态与修复记录），后续每次重构都以它为准绳。同期还有 `性能优化与重构报告-2026-10-27.md`（热路径等价优化）与 `代码审查与优化建议-2026-10-28.md`（P0 级体验缺陷清单，含「任务生命周期绑在 Activity 上」这类真实可用性问题）。

### 任务 C：修掉「命令已经执行成功，调用方却拿到失败」

**当时要解决的问题**：Shizuku 通道下注入命令、闹钟/日历写入、应用管控、`settings` 操作全部报 `shell 执行异常: process hasn't exited`，但现场看命令其实生效了——最恶劣的一类 bug：**副作用已经发生，回执说没发生**。

**我的判断**：不要在外层加 try-catch 把它吞掉，也不要盲目加长超时。先确认「谁抛的异常、为什么第一条轮询就逃出循环」。

**TRAE 具体做了什么**：顺着 `process.waitFor(30s, MILLISECONDS)` 往下读，确认 `ShizukuRemoteProcess` 没有覆写 `Process.waitFor(long, TimeUnit)`，于是落到 JDK 默认实现——默认实现只捕获 `IllegalThreadStateException`，而 Shizuku 客户端 `exitValue()` 经 Binder 抛的是 `RuntimeException("process hasn't exited")`，首个轮询就直接逃出等待循环，被外层 `catch` 收成失败。改成自轮询 `waitForExit()`：两类「仍在运行」异常都继续等，超时才 `destroy` 并按超时失败返回。

**最终体现**：提交 `fix(provider): 修正 Shizuku 进程等待逻辑，命令已执行却判失败`，恢复注入命令实跑与系统写入的可信回执。

### 工程化配套（TRAE 侧的长期收益）

- 26 份设计方案落在 `.trae/documents/`（编码环境、页面记忆、动作模式、提示词系统、Shizuku 集成、宽屏布局…），设计与实现同仓可追溯；
- 两个项目级 skill 固化重复劳动：`android-build-apk`（构建 + 版本号自增 + **从产出的 APK 实测** `aapt2 dump badging` 校验版本、时间戳重命名、构建成功自动发 dev 频道）、`hpa-publish`（dev/beta/nightly/stable 五频道发布到自建市场与官网）；
- 构建期闸门：`verifyProviderAssets`（Provider 资产指纹不一致即构建失败）、`checkDetektBaseline`（基线只减不增）——把「人会忘」变成「构建会拦」。

## 三、印象最深的一段：在手机里把 APK 打出来

**背景与处境**。项目做到中期，手机操控链路已经能在真机上跑通，但有个天花板很明显：用户改一行代码，还是得回到电脑。我想做的事很朴素——**让这台手机自己把自己的代码编译出来**。当时它看起来几乎不可能：Android 10 之后 `targetSdk ≥ 29` 的应用不能 `execve` 私有目录里的二进制，而主应用是 targetSdk 36；手机上没有任何 JDK、Gradle、Android SDK；`aapt2` 官方只发 x86_64，我的机器是 arm64。

**我承担的角色**。我是唯一的开发者，也是这个决定的唯一负责人。摆在我面前有两条路：一是「云编译」——把工程传服务器，编完下回来，一天能上线；二是「设备内编译」——可能要耗掉一两周，而且不保证成。我选了第二条，理由很直接：**云编译的尽头是「一个远程 IDE 客户端」，而设备内编译才是「手机能自己写自己的代码」**。这个产品定位的差别，值得赌一次。

**最难的一环**。不是装 JDK，也不是 PRoot 起 Alpine，而是 **arm64 上的 aapt2**。所有链路都通了，`Gradle` 一路跑到资源打包阶段就死，报的是「无法执行二进制文件」——因为 `aapt2` 只有 x86_64 版本。我盯着那条错误想了很久：要么放弃设备内编译（因为 Android 构建绕不开 aapt2），要么让 arm64 去跑 x86_64 的二进制。

最后选了后者：`qemu-x86_64` + glibc 转译。这不是「加一行配置」的事——要保证 qemu 在 PRoot 里有权限、要保证 glibc 的加载器路径对、要保证转译层的错误不会伪装成 Gradle 的业务失败。我把「aapt2 兼容层」写成了流程里的**显式一环**，而不是出错后手工糊上去的补丁，这样换设备、重装环境都能重放。

同一轮还顺手解决了两个「必须承认现实」的问题：环境组件是另一个 uid，读不到主应用的私有目录，所以构建前把工作区镜像到 `/storage/emulated/0/happyac-build/<工程名>`；`env` 组件的 targetSdk 只能固定 28，因为只有这样它才有资格执行自带二进制——这个 28 不是懒，是 W^X 逼出来的唯一解，我在 README 里专门写了一句解释，免得后来人以为是没升级。

**结果**。手机里第一次出现 `BUILD SUCCESSFUL` 那一刻，工程是从手机本地目录读的、JDK 是手机里的、Gradle 是手机里的、aapt2 是 qemu 转译的。不是"远程构建成功"，是**这台手机自己编译出了自己的下一个版本**。现在这条路已经固化成一条幂等流程，用户装完组件、开完权限，点一下就能出 APK。

**一个让我改掉坏习惯的细节**。同一时期做真机 E2E，我把「打开设置把字体调大」交给 AI，它卡在 vivo 的自定义字体滑块上**空转 52 步**——因为那个滑块不认标准的匀速 `swipe`，必须带初速度的 fling。我在旁边看着手机自己一遍遍滑同一个滑块，第一反应是"代码逻辑没错啊"。这件事之后我定了个规矩：**任何"应该能work"的判断，必须用真机证据推翻或确认**。于是有了 `BUGS/` 下 25 个带现场证据的缺陷单、vivo V2546A（Android 17）上的 L1–L5 分级用例，以及"动作连续未改变页面就触发人工接管"的阈值下调。这套方法后来反过来救了 aapt2 那一轮——因为我不再相信"看起来通了"，只相信手机上真跑出来的那行 `BUILD SUCCESSFUL`。
